# Plombir Git v0.4.3

This security maintenance release gives the instance signing key a random
identity and a history of every key the instance held, delivers security
notifications ahead of activity and bounds their queue, and tightens instance
administration: the last administrator cannot be removed, instance settings
changes are journaled and announced, and credentials can be revoked during
maintenance. Approvals of protected environments stop counting once their
approver loses read access, and the audit log no longer stores full webhook
URLs. SSH pushes carrying Git LFS objects no longer fail when the upload
outlasts the idle timeout.

## Before upgrading

Back up the database, repository storage, configuration and encryption key.
Upgrade frontend and backend together using the release bundle or a build from
the release tag. Installations upgrading from an older release must also follow
the [v0.4.2 notes](v0.4.2.md) and the earlier notes they link; an intermediate
deployment is not required.

## What happens on the upgrade

- **Two migrations run on the first start.**
  `m20261113_000001_instance_signing_keys` replaces the single
  `instance_signing_key` row with the table `instance_signing_keys`, one row per
  key the instance has held. `m20261113_000002_notification_delivery_priority`
  adds a priority class to queued notifications, classifies the rows already
  waiting, drops the index `idx_notification_delivery_due` and adds four:
  `idx_notification_delivery_class`, `idx_notification_delivery_kind`,
  `idx_notification_delivery_expiry` and `idx_notification_delivery_completed`.
- **The signing key identifier (`kid`) changes on the first start** if the key
  was derived from `jwt_secret`, as on every instance created before 0.4.3 that
  has not replaced its key with `rotate-instance-key`. The derived key is
  retired, a random key signs from then on, and the derived key leaves the JWKS
  (`/api/v1/ci/oidc/jwks`) after 10 minutes. An instance whose key was already
  replaced with `rotate-instance-key` keeps it.
- **Upgrade every server process at once.** A v0.4.2 process does not start on
  the migrated database (see the rollback item below). One that keeps running
  goes on signing with the key it loaded at start — on most instances the
  derived key, which leaves the JWKS after 10 minutes — so its CI OIDC tokens
  and attestations stop verifying.
- **Attestations signed before the upgrade verify on this server only.**
  `POST …/attestation/verify` keeps accepting them and reports the key as
  `retired`; a verifier outside the server no longer finds the key in the JWKS.
  Re-sign an asset that needs external verification: `POST …/attestation`
  replaces its envelope with one under the active key.
- **A rollback is a restore from backup.** v0.4.2 refuses to start on a
  database migrated by v0.4.3: its migrator stops at migrations it does not
  know, and the old key table is gone. Stop the server and restore the backup
  taken before the upgrade together with the previous image. `down` of the key
  migration carries only the active key back; the history of retired and
  revoked keys is lost with it.
- **New `409` refusals.** `PATCH /admin/users/{id}` and account deletion answer
  `409` when they would leave the instance without an active administrator.
- **Maintenance mode lets credential revocation through.** Deleting a personal
  or bot token, an SSH key or a deploy key, and `POST /users/logout`, work
  while maintenance mode is on. Every other write, sign-in included, still
  answers `503`.
- **An SSH push may wait longer for its client.** Between the ref
  advertisement and the client's first command the client runs its
  `pre-push` hook, where Git LFS uploads. That wait is no longer cut off by
  `[timeouts].git_idle_secs` (30 s by default); it is bounded by
  `git_stream_secs` (300 s by default), and the exchange after it gets a fresh
  `git_stream_secs`. With `git_stream_secs = 0` the wait is still bounded, at
  300 s, and only the exchange is unbounded. A silent push therefore holds its
  session for up to 300 s instead of 30 s.

## Instance signing key

The key signs release-asset attestations and CI OIDC tokens. A new
installation generates it at random; it is sealed with the encryption key and
kept in the database, and rotating `jwt_secret` no longer touches it. The
database keeps every key the instance has held as a public half; only the
active key keeps its sealed private half.

- `instance-key-status` lists the keys with their `kid`, status and origin
  (`generated`, or `legacy_derived` for a key computed from a JWT secret).
- `rotate-instance-key --reason routine` retires the active key: it keeps
  verifying its attestations on this server and stays in the JWKS for
  10 minutes.
- `rotate-instance-key --reason compromised` revokes it: it leaves the JWKS at
  once, and its attestations are reported as `revoked`.
- `revoke-instance-key <kid> --yes` revokes a retired key. If a `jwt_secret`
  used before 0.4.3 may have leaked, revoke the `legacy_derived` key; the
  active key is random and unaffected.

A running server picks up a rotation within 30 seconds; no restart is needed.
In that window a server process can still sign with the key it had loaded. The
JWKS is served with `Cache-Control: public, max-age=300`, so a relying party may
keep a retired key for about 15 minutes after a rotation and a revoked key for
up to 5 minutes; after a revocation, ask relying parties to refetch the JWKS.
Relying parties that pinned the public key instead of reading the JWKS must
update the pin. See [Secrets and rotation](../install.md#secrets-and-rotation).

`POST …/attestation/verify` reports the new status `revoked` and the fields
`key_status` and `key_origin` of the key that signed.

## Notifications

Queued notifications are delivered by class: the account's own credentials and
factors first, then security of shared resources, then activity. One recipient
takes at most five rows of a delivery page in the security classes, and the
other classes keep a share of every page. Security notifications are bounded
when queued, keeping the oldest: five of one kind and fifty of one event per
recipient, and warnings to a previous destination have a budget of their own.
A row past a bound is recorded as `cancelled` with `coalesced`, without a
payload.

Pending notifications, including the warning to a previous destination, are no
longer cancelled when an account deletion starts; they are delivered if the
deletion fails, and removed with the account when it completes.

Known limits, described in [Delivery order and limits](../notifications.md#delivery-order-and-limits):
there is no per-actor budget, so one account that reaches many recipients can
still delay their shared-resource notices and activity (never their own
credential warnings); a flood of one event can drop a simultaneous genuine
event of the same kind for the same recipient; and dropped rows still leave
terminal rows for 30 days.

## Administration

- An instance keeps at least one active administrator: demoting, deactivating
  or deleting the last one is refused with `409`, also when two such requests
  race. An administrator locked out after failed sign-ins still counts. If the
  only administrator cannot sign in, run `plombir-git create-admin` on the host
  to promote or create another.
- `PATCH /admin/settings` keeps its access contract. A change is recorded in
  the audit log as `admin.update_settings` with the values before and after,
  and every administrator is notified that maintenance mode or the banner
  changed; the notice does not carry the banner text. A request that changes
  nothing records nothing.
- Creating an administrator through `POST /admin/users` or
  `plombir-git create-admin`, or promoting an account with `create-admin`,
  notifies every administrator.

## Protected environments

An approval of a protected environment counts only while its approver can
still read the repository. A vote cast by an approver who was later removed
from a private repository, or who is outside a repository that became private,
no longer counts toward the threshold, even if the approver is still on the
allow-list. The vote stays in the approval history.

## Audit log and webhook URLs

New audit rows for webhooks record the origin (`scheme://host[:port]`, without
user information) and the webhook id, plus `url_changed` and the previous
origin when an update moves the hook. Rows written before this release still
contain the full URL, whose path or query may hold the receiver's secret. They
are not rewritten. Find them with:

```sql
SELECT id, action, created_at FROM audit_log WHERE details LIKE '%"webhook_url"%';
```

Decide whether to redact those rows or to rotate the receivers' secrets.

## Manual smoke checklist

- [ ] On an instance with several server processes, all of them were upgraded
  together and none still runs v0.4.2.
- [ ] `/readyz` succeeds and `/api/v1/instance` identifies the release commit;
  the server, runner and MCP binaries report `v0.4.3`.
- [ ] Ordinary Git clone/push, issues, PRs and authorized CI still work.
- [ ] `instance-key-status` shows one `active` key of origin `generated`; on an
  upgraded instance the former key is `retired` with origin `legacy_derived`.
- [ ] The JWKS lists the active key, and the retired key only during the first
  10 minutes after the upgrade.
- [ ] An attestation created before the upgrade verifies through
  `…/attestation/verify` with `key_status` `retired`.
- [ ] Demoting the only administrator answers `409`; with a second
  administrator it works.
- [ ] Turning maintenance mode on writes `admin.update_settings` to the audit log
  and notifies the administrators; a token can be revoked while it is on.
- [ ] A security notification is delivered while activity notifications are
  queued.
- [ ] An SSH push whose Git LFS upload runs longer than `git_idle_secs`
  succeeds.

Keep the previous image and matching data/configuration backup for rollback.
Rolling back removes these security protections and, because of the
migrations, needs the database backup taken before the upgrade.
