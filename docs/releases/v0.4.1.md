# Plombir Git v0.4.1

This release conceals inaccessible repositories, strengthens access and security
administration, and adds durable notices for those changes. It also fixes the
first-login password replacement screen.

## Before upgrading

Back up the database, repository storage, configuration and encryption key.
Upgrade the frontend and backend together using the release bundle or a build
from the release tag. There are no new database migrations relative to v0.4.0.
An installation upgrading from an older version must also follow the
[v0.4.0 upgrade notes](v0.4.0.md); an intermediate v0.4.0 deployment is not required.
Keep the existing encryption key and stop every server before a separate rekey.

## Authentication changes for administrators and API clients

Repository collaborators, organization members and teams, visibility changes,
transfers/deletions, webhook/mirror configuration, branch/tag protections,
CI secrets/environments and destructive account/bot administration now require a
login session with fresh proof. With MFA enabled, that proof must match the
current factor; password alone is insufficient. Existing user-verified passkeys
can also supply proof. Confirmation remains valid for ten minutes, so a second
operation within that window need not show another prompt.

**Compatibility change:** personal access tokens, including tokens with `repo`
or `admin` scope, cannot perform these protected administrative mutations.
They receive 403; adding scopes does not bypass the requirement. Clients using
login sessions must handle `403 sudo_required` through fresh authentication.
Revoked sessions still receive `401 session_revoked`.

Ordinary Git/CI execution, repository descriptions and CI variable automation
keep their existing authorization. Emergency token/key revocation remains
available without a new confirmation. See the precise boundaries in
[features](../features.md) and [API documentation](../api.md).

Removing an organization member now removes their team memberships in the same
transaction. Inviting them back does not restore old team administrator rights.
Non-members cannot be preassigned to teams; old dormant rows are excluded from
team expansion and cleared on admission.

## Notifications

Eight new categories bring the total to 44: repository/organization access,
repository/organization security, webhooks, mirrors, CI security and instance
administration. Owners and affected accounts receive appropriate copies. Queuing
and the underlying mutation commit together. Messages contain no integration
credentials or CI values, and another authenticated actor's IP/device is omitted.
Login/reset/confirmation events are attributed to their own proof, even if the
browser carries another account's cookie.

New categories default to email on. If Telegram is configured and confirmed,
missing new choices inherit the saved Telegram choice for notification-settings
changes. Explicit choices always win. Review the new switches after upgrading;
use each category's test button to verify your selected destinations.

Transfers retain repository-bound collaborators, keys, hooks, mirrors and CI
settings/secrets. Prior principals' notices use the old namespace. This release
does not introduce transfer acceptance or destroy existing private forks/local
clones when source access is revoked. See [notification behavior](../notifications.md).

## Manual smoke checklist

- [ ] `/readyz` succeeds; `/api/v1/instance` reports the release source commit.
- [ ] Signed-out and unauthorized accounts see the same full-page 404 for a
  private repository and a made-up name, without tabs or clone controls.
- [ ] REST API requests with no access have the same 404 for hidden/missing
  names. Git/LFS may challenge for credentials in both cases before authentication.
- [ ] First login with an administrator-set password asks for a new password
  without a misleading "Login failed" banner.
- [ ] After the ten-minute proof window expires, adding/changing/removing a
  collaborator asks for fresh authentication; cancelling leaves access unchanged.
- [ ] With MFA enabled, password alone cannot authorize the change. After valid
  proof the intended change succeeds and the owner receives its enabled notice.
- [ ] A `repo`/`admin` PAT cannot bypass the new sensitive-action guards.
- [ ] Removing and re-inviting an organization member leaves old team privileges
  removed until explicitly granted again.
- [ ] The eight new notification categories appear; email/Telegram tests succeed
  for the channels enabled on the account.
- [ ] Git clone/push, ordinary issues/PRs and CI still work with their usual rights.

Keep the previous image and matching data/configuration backup for rollback.
Rolling back removes these security protections; stop the server and restore a
consistent backup/image pair rather than switching a running deployment blindly.
