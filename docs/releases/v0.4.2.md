# Plombir Git v0.4.2

This security maintenance release strengthens credential-change transactions,
Git HTTP authorization after uploads, private-fork pull requests and automated
merging. It also restricts draft-release visibility and includes push-mirror
credentials in encryption-key checks and rotation.

## Before upgrading

Back up the database, repository storage, configuration and encryption key.
Upgrade frontend and backend together using the release bundle or a build from
the release tag. There are no new database migrations relative to v0.4.1.
Installations upgrading from an older release must also follow the
[v0.4.1 notes](v0.4.1.md) and, when applicable, the
[v0.4.0 notes](v0.4.0.md); an intermediate deployment is not required.

**Previous encryption-key rotations:** if you rotated the key on v0.4.1 or
earlier and use push mirrors, retain the original key. Earlier versions could
leave push-mirror passwords encrypted with it. Stop every server process and
follow the [recovery procedure](../install.md#secrets-and-rotation) using the
fixed binary, the original key as `--old` and the current configured key as
`--new`. Inspect `--dry-run` before applying: `push_mirrors.password_encrypted`
must be listed, and values already encrypted with the current key are counted
as `already_new` and left unchanged. Without the original key, re-enter the
affected mirror credentials; ciphertext alone cannot recover them.

## Accounts and authentication

- Deactivating an account revokes existing sessions and pending address-change
  links. Reactivation does not restore them. PATs, SSH keys and passkeys remain
  suspended while inactive and can be used again after reactivation.
- Password changes/resets and operator factor resets cancel pending
  account-email changes atomically. Address changes consume their link in the
  same transaction and invalidate reset links for the previous address;
  in-flight issuance cannot recreate a link from stale account state.
- Operator factor resets revoke sessions, TOTP material, unused backup codes,
  passkeys and pending address changes together with their notifications.
  A passkey ceremony already in flight cannot finish against the new account
  generation.
- Password-only verification does not clear second-factor failures. Successful
  reauthentication clears counters only while the completed proof still
  matches the account, credentials and lockout state.
- Session revocation, account-standing and identity-conflict checks apply to
  every supported Authorization format, including Cargo's raw credential form.

The fresh-proof requirements introduced in v0.4.1 remain in force.

## Repository access and pull requests

Positive repository permission decisions are no longer cached. Subsequent
checks observe revocation across database pools and server processes, at the
cost of fresh indexed grant queries. Repeated refusals are cached for at most
five seconds, so a grant made through another pool may take that long to appear.

Git HTTP fetch and push recheck the credential, account, repository identity
and access after receiving the request body. Push also reloads branch/tag,
mirror and token restrictions. Work admitted after that check can still finish
if access is revoked later; this is not an atomic barrier around running Git
processes. LFS, SSH and registry upload lifetimes are separate contracts.

The author of a PR from a private fork must retain write access to that source.
Revocation, a downgrade to reader, deactivation or removal of the source freezes
updates and blocks CI and merging. Existing PRs opened with read-only source
access also freeze after upgrading. Previously fetched snapshots remain
readable while their objects are retained, with a source-unavailable notice;
missing snapshots return `409 head_source_unavailable`. Already copied objects
are not erased. Public-fork and same-repository PRs keep their existing source
access behavior.

Merge-queue and auto-merge operations require explicit approval of the current
fork head by an active human with write access to the base repository, even
without a CI workflow. Enqueueing is not approval. A new head or revoked
approver requires fresh approval; a previous successful pipeline does not
replace the check. Failed queue entries must be approved and enqueued again.
Auto-merge waits for approval, and cancellation cannot be undone by a late
background recovery. See [fork CI behavior](../gitea-actions.md) and the
[precise access boundaries](../features.md).

## Visibility and namespace changes

Draft releases, notes, assets and attestations are visible only to repository
writers. Other readers receive the same `404` as for missing resources, and
lists and totals omit drafts. A CI job token alone does not grant draft access;
workflows reading drafts need an authorized writer credential. All release
reads, including published public downloads, now use `private, no-store`.
Configured webhooks remain trusted integrations and still receive existing
`release.created` metadata for drafts.

Organization visibility accepts only `public` or `private`; an invalid PATCH
changes no fields. Historical unknown values are member-only and produce a
startup warning so owners can correct them. Creating organizations or bots
reserves usernames present in enabled LDAP directories, including members who
have never signed in. An unavailable configured directory makes creation fail
closed with `502`, rather than claim a potentially reserved name.

## Manual smoke checklist

- [ ] `/readyz` succeeds and `/api/v1/instance` identifies the release commit;
  the server, runner and MCP binaries report `v0.4.2`.
- [ ] Ordinary Git clone/push, issues, PRs and authorized CI still work.
- [ ] A session used before account deactivation stays revoked after
  reactivation; a new authorized login works.
- [ ] Password/factor changes invalidate pending address-change links;
  completing an address change invalidates old reset links.
- [ ] A draft release is visible to its writer but absent from reader lists,
  direct links, assets and attestations. Published releases remain readable.
- [ ] A fork head without current approval cannot run merge-group CI or merge
  automatically. Current approval allows the intended work; a new push needs
  approval again.
- [ ] Revoking a private-source author's write access freezes updates and
  blocks merging; any retained diff is clearly marked as a previous snapshot.
- [ ] LDAP-reserved organization/bot names are refused, and a directory outage
  gives an explicit failure without creating the owner name.
- [ ] If an older rekey affected push mirrors, the offline recovery report
  includes their encrypted passwords before the old key is retired.

Keep the previous image and matching data/configuration backup for rollback.
Rolling back removes these security protections. Stop the server and restore a
consistent backup/image pair rather than switching a running deployment blindly.
