# Plombir Git v0.4.0

This release adds personal Telegram delivery alongside email, security alerts,
Russian localization and remembered browser sessions. It strengthens MFA for
sensitive account changes and fixes session recovery, security settings and
repository navigation. Optional bot agent profiles and a configurable advertised
SSH clone port are also included since v0.3.0.

[CHANGELOG.md](../../CHANGELOG.md#040---2026-11-07) describes the changes.

## Before you upgrade

1. Back up the database, repository storage and configuration, including the
   encryption key. Stop all instances using a file-backed SQLite database before
   migrating it. Upgrade the frontend and backend together; follow the offline
   procedure in [the deployment guide](../../deploy/README.md).
2. Apply the two migrations listed below. A server already running the accepted
   notification candidate has these tables; migrations are not repeated.
3. Keep the existing encryption key. Agent model keys, Telegram bot tokens and
   queued warnings use it. A separate key rotation requires **all servers using
   that database to be stopped**, then restarted with the new key. A dispatcher
   left running with the old key can permanently discard a pending warning.
4. Telegram requires direct outbound HTTPS to `api.telegram.org`. Its client
   deliberately ignores HTTP(S) proxy environment variables and follows no
   redirects. SMTP remains optional; no new instance TOML section is required.
5. For a reverse proxy exposing SSH on a different port, set `[server].ssh_clone_port` to the external port. Keep `ssh_port` as the actual listener
   port. Existing configuration remains valid when no mapping is needed.

## Account and client behavior

- With MFA enabled, disabling or replacing the authenticator, regenerating
  backup codes, changing password/email and other protected credential actions
  require fresh proof of the current factor. Confirmation lasts ten minutes.
  Existing MFA sessions will confirm once after upgrading; password alone cannot
  disable MFA. An existing passkey with user verification also supplies proof.
- Enabling MFA does not revoke other ordinary sessions. Sign out to revoke all
  browser sessions if compromise is suspected. Automation and emergency key or
  token revocation retain their existing permission checks.
- A live cookie and explicit signed session credential naming different accounts
  produce `identity_conflict`; the browser rechecks its account without replaying
  the rejected action. Cookie-only tabs still follow the browser's current
  account. Use separate browser profiles for simultaneous accounts.
- Remembered sessions renew on navigation for up to 30 days of inactivity, with
  a 90-day absolute lifetime. Renewal does not extend sudo. Clients omitting
  `remember_me` retain the previous policy. The UI/API must share an origin for
  cookie renewal.
- Personal notification settings, including the legacy email-only endpoint,
  now require a login session; PAT automation cannot change or test them.

## Notifications

There are 36 activity and security events. Each has independent email and
Telegram switches and a test action. The language at save time is used for
messages. Connecting Telegram copies the email selections; replacing an already
configured destination preserves custom choices. Select all / Deselect all
operate on one block and channel at a time.

Changing the Telegram destination or reducing delivery requires fresh
confirmation; with MFA enabled it must prove the current factor. A confirmed
previous destination receives a minimal warning even when delivery was disabled.
Existing email preferences are preserved. New security email events default on;
Telegram is off until connected.

The first completed login from each browser/account after upgrade can trigger a
new-device alert: existing sessions do not seed the known-browser list. Each
full login without a browser witness also alerts; API/CLI login clients should
retain cookies if they want browser recognition. PAT access is not a new login.

Activity email now uses per-event durable delivery rather than the old digest.
Old pending email without a captured destination remains visible in-app but is
not sent after upgrade. Delivery retries are bounded to six attempts and 24
hours. See [notification operations and API behavior](../notifications.md).

## Verification and rollback

After migration, check `/readyz`, `/api/v1/instance` and the binary version.
Verify sign-in, a protected MFA action, repository access and a notification test
for each configured channel. The first new-device message after upgrade is
expected.

Keep the old image digest and matching pre-upgrade data/configuration backup.
Rolling back to v0.3.0 means restoring that backup while stopped and starting its
matching image; do not run the old server against an upgraded database. The
moving `latest` tag is not a rollback reference. Linux amd64/arm64 binaries, the
multi-architecture image, deploy bundle, checksums and attestations are published
by the Release workflow for this tag.
