# Plombir Git v0.3.0

A typical `.github/workflows` now runs here as written: steps in their own
processes, outputs, matrices decided at run time, `services:`, composite and
JavaScript actions such as `actions/setup-node`, `on: schedule`, `vars.*` and
`permissions:`. Imports from Gitea and Forgejo bring the whole project, as
imports from GitHub and GitLab do, and every import answers with a receipt of
what came over. `plombir-git trial` starts a throwaway instance with one
`docker run`, and merges name the people who wrote and merged the work.

[CHANGELOG.md](../../CHANGELOG.md#030---2026-10-23) lists every change. This
page lists what to do about them.

## Before you upgrade

Work through this list on the running v0.2.0 instance, before the new image
starts.

1. **Back up the database and repository storage.** Twelve migrations run on
   the first start, and v0.2.0 does not know the tables and columns they add.
   File-backed SQLite migrations run while the server is stopped; follow the
   offline migration procedure in `deploy/README.md`.
2. **Drain and upgrade external runners.** The runner protocol is at 6, and a
   v0.2.0 `plombir-git-runner` sends none: it is never handed an Actions job
   again (the poll answers `426`, naming the job) and keeps taking only native
   `.plombir-git-ci.yml` jobs. Let running jobs finish, stop the runners,
   upgrade the server, then start the runners on the v0.3.0 binary.
3. **Some workflows start running.** Check which repositories carry them
   before the upgrade:
   - `.github/workflows/*.yml` now runs when a commit has no
     `.gitea/workflows`, and `.forgejo/workflows` runs first of the three.
     A repository imported from GitHub or Forgejo whose CI never ran here
     starts a pipeline on its next push.
   - `on: schedule` workflows run on the default branch, at most every
     `[ci] schedule_min_interval_minutes` (5) per `- cron:` entry.
4. **Secrets reach only the steps that name them.** An Actions job is given
   the secrets its workflow names, and each step only those the step, the job
   or the workflow names in `env:` or `${{ secrets.NAME }}`. A script that
   reads `$DEPLOY_KEY` from its environment without the workflow naming it
   gets nothing: add `env: { DEPLOY_KEY: ${{ secrets.DEPLOY_KEY }} }` to the
   step. Native jobs keep every secret.
5. **Workload identity needs `permissions: id-token: write`.** A workflow
   that declares no `permissions:` gets `contents: read` and `packages: read`
   and no workload identity, and `/api/v1/ci/oidc/token` refuses its token.
   Any `write` other than `id-token: write` (`contents: write`, `write-all`)
   is refused when the workflow is read: push or release with a deploy key or
   a token kept in a secret. Native jobs keep their workload identity.
6. **Actions from github.com are off by default.** `uses: owner/repo@ref`
   loads from this instance's public repositories and the workflow's own
   unless `[ci] actions_sources` also lists `"upstream"`, which fetches from
   `actions_upstream_url` (`https://github.com`). A workflow that uses
   `actions/setup-node` or any other action from GitHub is refused by the
   source's name until then. `actions/checkout`, `actions/cache` and
   `actions/upload-artifact` stay built in. Allow `"upstream"` only for a
   forge whose actions you would paste into a workflow yourself; consider
   `actions_require_full_sha = true`.
7. **Steps are processes of their own.** A variable a step `export`s, a
   directory it `cd`s into and a shell option it sets end with the step; use
   `$GITHUB_ENV` and `$GITHUB_PATH`, as on GitHub. A step without `shell:`
   runs under `bash -e`. `::set-output` is refused; write to
   `$GITHUB_OUTPUT`. In expressions `&&` and `||` give back an operand rather
   than `false`, and a job whose needed job was skipped is skipped too.
8. **Merges are signed by people.** The committer of a merge, squash or
   rebase is the account that merged it, a squash is authored by the pull
   request's author, and its message is `<title> (#N)` with the description.
   Hooks or reports that look for `Plombir Git <noreply@plombir-git.local>`
   find it only on the merge queue's rehearsal commits, which never reach a
   branch.
9. **A stopped runner stays registered.** `SIGTERM` marks it offline instead
   of deleting it. Revoke a runner with `DELETE /admin/runners/{id}`; one you
   expected the stop to remove is still listed.
10. **Webhook `ci.status`** sends `repository: "<owner>/<name>"` where it sent
    `repository: "repo#<id>"`. `repository_id` is unchanged.

## What changes for clients

- **Runner protocol.** A runner sends `x-plombir-git-runner-protocol`; steps
  need 2, `services:` 3, scoped secrets 4, JavaScript actions 5 and composite
  actions' files 6. A job needing more than a runner sends is never handed to
  it.
- **Job token.** `CI_JOB_TOKEN` carries the job's `permissions:`;
  `CI_OIDC_TOKEN_URL` is set only for a job that may use it.
- **Rootless Docker.** On a rootless daemon a job container runs as the
  container's root, which the daemon maps to its own user on the host and the
  workspace's owner. A rootful daemon runs jobs as before.
- **Pipelines API.** `GET /pipelines` and `GET /pipelines/{id}` add
  `commit_message` and `run_name`; jobs add `display_name` and their steps,
  each step's log at `…/jobs/{job_id}/steps/{number}/log`.
- **Imported rows** carry `original_author`, `original_author_id` and
  `original_service` (`github`, `gitlab`, or `github:<host>` /
  `gitlab:<host>` / `gitea:<host>` for another server).

Every one adds tables or nullable columns and none refuses on existing data.
Rows written before the upgrade read as before: pipelines and jobs without
steps, names or outputs, pull requests without `base_sha` (a merged one is
then diffed against its merge commit's first parent), imported rows without a
byline.

## Rollback

Test a restore before relying on rollback. Rolling back means restoring the
pre-upgrade database and repository backup and starting the v0.2.0 image
pinned by digest, with runners back on the v0.2.0 binary: v0.2.0 does not
know the tables and columns above. The moving `latest` tag is not a rollback
reference.
